# Implementation review — 11 October 2026

## Conclusion and scope

The core paper method is implemented. The immediate obstacle is a fragile and expensive execution path, followed by very slow motif matching and an incomplete recovery contract. No complete real-data MCM has reached neural training. More compute alone would not repair the entry failure, and two workers alone would not make the currently observed workload practical.

This review covers current installed source, retained numerical/resource outcomes, and three independent bounded source audits. It does not report newly executed tests, benchmarks, financial fits, data-array inspection or external recovery. The installed-source baseline is Main `dd0d8d4cda7bffa6e45629f00da5ce60412cbec1`, branch `research/onchain-paper-replication-2026-09-24`. Uninstalled candidates are distinguished from installed behavior. No source implementation or empirical launch occurred during this review.

The next useful milestone remains **one representative real-data end-to-end pilot**: original 32 motifs and 512 spent samples, all seven whole graphs, all 415,968,128 MCM cells, trainable MCM MLP → directed GAT → mean pooling → attention LSTM, and an actual joint update/checkpoint. A smaller engineering qualification can establish a seam's correctness or speed; it cannot replace this milestone. A resource update is not a 100-epoch financial fit.

The [implementation plan](../../docs/superpowers/plans/2026-10-11-onchain-pilot-efficiency.md) addresses this milestone. The original [13-task plan](../../docs/superpowers/plans/2026-09-24-onchain-paper-replication.md) and [C01–C18](REPLICATION_SPEC.md) continue to govern the broader replication.

### Checks that should remain, and checks that can be made cheaper

Scientific checks remain necessary: matching feasibility/objective against an independent reference; frozen tolerances; directed graph aggregation; train-only dictionary/scalers; chronological availability; joint gradients; complete failure/unavailable denominators; exact saved-checkpoint replay; real enforced resource limits and process cleanup; actual recovery before deletion. Runtime source/claim/body currentness is also necessary, but its **chosen frequency and implementation** can be improved with an explicit reviewed contract.

It is not necessary to impose universal bitwise equality on every future accelerated implementation. C05 requires float64 scalar agreement at `atol=1e-8, rtol=1e-6`; C06 requires applicable accelerated float32 agreement at `atol=1e-5, rtol=1e-4`, with tie feasibility/score criteria. Existing exact seam tests remain valuable regressions. A new tolerant accelerator needs a declared route and independent comparison; it cannot quietly weaken the currently selected exact path or widen tolerances after observing failures.

Nor is it necessary to repeat unchanged reviews, rebuild generic launch frameworks, duplicate historical stores, or run the entire old test matrix after every small edit. Focused changed-seam tests, one combined source/entry review of a coherent frozen bundle, and incremental preservation with existing reviewed tools are appropriate. No successful-validation cache, metadata-only replacement for payload authentication, or stale timestamp reset is justified.

## Performance and compute implications

Pilot34 retained nine partial batches:36,864/415,968,128 cells,35,744 computed and1,120 reused; summed numeric elapsed5,215.995s and guard elapsed10,775.518s. Its recent6–8cells/s is a partial-prefix diagnostic, not whole-job throughput. Initialization, guards, other phases and interruption prevent attributing the entire difference to checking. One retained first-batch observation placed internal authority polling at2,192.79s of3,915.77 numeric seconds, approximately56%; that is specific to that batch.

At6–8cells/s, naïve division of the full denominator gives roughly602–802days for features alone. This is **not an ETA**: geometry, cache, guard, offload and training costs are not stationary or fully measured. It does establish an order-of-magnitude problem. Finishing those features in seven days would require about688 useful cells/s; in24hours, about4,814cells/s. These are capacity decision thresholds, not promises or changes to the scientific scope.

Perfect two-worker scaling would at most double a CPU-dominated component, and cannot yield the roughly86–115× increase needed to reach688cells/s from6–8. The current C extension's finite engineering kernel result was about1.16× on a tiny case; no real whole-pair saving follows. An exact overhead reduction may be material, but even removing half the runtime does not solve a100× gap. Algorithmically faithful batching/vectorization or substantially different compute may ultimately be required.

The current job has a6GiB cgroup maximum,5GiB memory.high, zero swap, two CPU IDs and200% quota. Relative to the sampled35 peak, only1,120,833,536B remains below the hard maximum; this is not demonstrated worker headroom. The physical host's16GB and an idle MemAvailable sample near11GB do not enlarge that job limit. Spawned workers must receive bounded local pair arrays, not duplicate weekly populations or import the entire neural stack. Large pairs require a predeclared serial fallback under the same method, with no dropped cells.

GPU purchase/rental is premature before profiling. Python-object C loops will not automatically run on a GPU. A GPU route needs a real batched numeric implementation, memory/precision qualification and the same objective/schedule. Distributed CPUs could partition independent pair work, but deterministic publication, genuine parent authority, storage reservation, transport/recovery and worker overhead must be measured. Independent model fits become naturally parallel only after features, data and capacity are admitted. No paid resource is authorized by this review.

## Data, model and storage details requiring attention

- **Clocks and scaler scope:** `dataset.py` rejects missing/late expected weeks rather than carrying older graphs forward. Retrospective CoinMetrics PriceUSD has assumed next-midnight availability, not proven historical publication. The resource pilot flags `full_fold_population=false`, `full_fold_scaler=false`, `paper_financial_fits=0`; those distinctions must survive reports and continuations.
- **Joint training:** Learned graph features must be regenerated after each optimizer update. Repeated graph references may share a single forward computation, while gradients accumulate from all occurrences. Removing retained graph populations or caching detached embeddings is not an acceptable memory shortcut.
- **Aggregation:** ETH float-value handling is an explicit approximation; BTC projection uses rational arithmetic before feature conversion. Both need full admitted raw-to-graph denominators for broad completion; graph transaction fees are not strategy execution costs.
- **Storage:** A fresh free-space observation is not a reservation or external recovery. Current35 declaration includes13,552,489,053B new allocated growth and10,989,900,877B logical growth, plus650,016 entries. Typed maxima are workflow envelopes, not simultaneous local allocation. Do not substitute the earlier conditional55.44GB figure without its original assumptions. Record input residency, temporary/checkpoint/log growth and external transfer/recovery separately. Preserve the10GiB floor.
- **Exception and process semantics:** First-error retention, ordered result publication, bounded checkpoint handoffs, dead-child detection and actual reap/cgroup closure become more important with workers. Scientific authority remains in the real parent; workers compute, they do not fabricate Owner/Binding/ResearchRun claims.

## Recommended implementation order and stopping criteria

1. Preserve/review/recover35's actual failed increment; reconcile current accounting and evidence. No historical store recopy or framework rewrite.
2. Add bounded exclusive phase telemetry and correct the observed serial input-admission boundary. Qualify long/mutating reads, stale-before/during checks and primary-error retention offline before another real attempt.
3. Implement completed-prefix continuation and a single-pass storage monitor, with failure-injected durability and exact scope checks. Retained completed work must be reusable without reopening a spent identity.
4. Use profiling to select the dominant metadata/numeric seam. Qualify a genuinely numeric accelerator against applicable frozen criteria. Do not automatically install every source-only candidate.
5. Add at most two bounded workers only once serial preparation is reliable and memory/authority/ordering are explicit. Require measured useful end-to-end gain, not CPU utilization alone.
6. Run one fresh reviewed real pilot with observable milestones: first batch → whole graph → seven whole graphs → joint update/checkpoint → independent review/recovery. Report feasibility and compute requirements from these measurements.
7. Admit full-fold ETH/comparators and then broader paper coverage under the original plan. Accuracy does not decide whether work is completed or skipped.

If a bounded engineering change does not improve whole-pair/whole-batch time, leave it unselected. If serial preparation still cannot fit its explicit lease contract, stop empirical relaunches and resolve that seam first. If full-workload throughput remains impractical, retain the whole goal and identify the concrete kernel/compute requirement rather than promising eventual completion. An eight-hour job limit is not a feasible completion strategy for a non-resumable workload whose measured prefix suggests months.
