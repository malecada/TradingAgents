# Maintained ownership and successor handoff

Three independently accepted candidates are now maintained modules:
`matching_owner.py`, `matching_death.py` and `matching_ancestry.py`. The original
dated sources, tests, failures and reviews remain unchanged. `promotion.json`
records the initial ordinary-import/root adaptations; retained promoted source
snapshots distinguish that move from the subsequent successor extension.

`matching_owner.open_successor` now joins an actual active `ResearchRun` to its
registered fit route, version2 producer plan, exact scalar backend and policy,
complete current source closure, compatible committed numerical anchor, runtime
inventory and current guard owner. The execution source is the new actual claim;
the compatible earlier numerical anchor remains a distinct context field. No
source identity is spoofed to obtain checkpoint compatibility.

Before any successor journal publication, the current worker must pass its guard
lease, exact command/owner/resource policy and monitor PID/start-tick checks. The
full registered failed ancestry and predecessor death proofs then pass under the
lifecycle lock. The immediate failed journal must still match its admitted hash.
The current claim and guard are refreshed immediately before creating exactly one
`FeatureJournal`. Owner/start/claim publication is exclusive. A later publication
or binding failure preserves the partial directory and refuses automatic retry;
the outer lifecycle owner remains responsible for terminal closure.

The new ancestry option can check that exact current child journal alongside all
failed predecessor siblings. It joins current owner/start/claim and inherited
parent/workflow identity rather than merely allowing another directory. A live
binding checks both the current guard and predecessor death/evidence on each
lease call, including all sibling and optional terminal inventories. Full check
also verifies the current source, inputs, numerical anchor and runtime. Neither
API is a persistent process lock; the outer guarded worker must hold exclusive
ownership and freeze source across numerical operations.

The created journal inherits the original parent metadata. It does not load,
copy or reinterpret historical checkpoint arrays. There is still no automatic
call from the existing registered feature producer to this new interface.
Dictionary/MCM workload membership, pair-journal/extent integration, orphan
reconciliation, full workflow quotas, numerical checkpoint loading and consumer
routing remain required before empirical matching. No financial fit is launched.
