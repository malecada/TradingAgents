## Fixed motif-side reuse

The32 motif objects and identities are already materialized once; imported_kernel computes typed motif identities outside the center loop. Endpoint index layouts could be shared, but agreement is `exp(-fsum((float(x)-float(y))**2)/width)` and depends on each left feature vector. A motif-only norm/dot transform changes arithmetic; an edge-product cache is left-pair-specific. Node agreements already reside in V; accepted small-domain edge reuse removes repeated same-pair agreement calls. Larger exact lazy caching can remove repeated agreement evaluation within iterations but leaves every ordered multiply/add, normalization, rank, validation and per-pair publication. This is a bounded constant-factor opportunity with unknown whole-population eligibility, not a source-supported38,000× remedy.

## Concrete implementation seam and limit

The only concrete substantial computational candidate identified is a private compiled replacement for matching_annealing._advance_checked's *uncached edge-chunk body* (lines145-190), returning to the same Python state machine at the same operation budget/phase cursor. It could remove Python feature-generator/index-loop overhead while maintaining edge order, per-term subtraction/square, exact CPython math.fsum behavior, the same math.exp, .5 multiplication followed by M multiplication, and sequential destination additions. It must preserve lazy exception-prefix publication, NumPy error-policy fallback, beta schedule, existing SciPy normalization, scratch reservation and all operation counts. No fast-math/FMA, vector reassociation, alternative fsum/exp, cross-pair batching/reordering or earlier eager agreement failures are allowed. Calling the original Python fsum/exp with ordered scalar terms is the safest semantic starting point, but retains substantial Python work; reimplementing them natively requires platform-specific exactness proof. This is a responsible seam for later engineering, not an implemented or validated speedup.

Even ideal zero-time numerical kernels leave mandatory per-cell callbacks. compact_matcher emits begin+complete events (at least831,936,256 events for this denominator), invokes all leases/retention checks and produces ordered score-tail acknowledgements. compact_pair_log._append retains stat/write/readback and durability-dependent fsync or acknowledgement; no unconditional per-event fsync assumption is made. Existing operation boundaries allow accelerating work *inside* an advance, not combining pair publications/checkpoints or skipping callbacks. No existing exclusive phase timing proves those remaining costs fit14,443pairs/s. Consequently neither compiler work nor exact memoization is a credible full-workload feasibility claim at present. Validation-once remains a separate small accepted/uninstalled improvement.
