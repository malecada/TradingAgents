# Independent registered pair integration requirements

Static review of the existing registered feature, lifecycle and isolated typed-pair interfaces. These are concrete prerequisites for integration, not approval of a registered matching implementation. No production files were edited, no tests or jobs were run, and no empirical or checkpoint array bodies were read. The maintained six-module promotion was not yet present when the source inventory was inspected; its implementation needs separate review.

## Material boundaries

1. **Numerical identity is not the existing retention policy.** `tradingagents/research/onchain_replication/matching_policy.py:1–23` admits only `score_only`, which preserves the accelerated solver. `registered_features.py:126` converts that policy into a boolean. The new scalar float64/SciPy backend must have an explicit versioned numerical identity. Do not route it through the old boolean or mix its scores into an existing accelerated MCM prefix. `feature_pipeline.py:68–73` and `registered_features.py:24–30` currently derive workflow identity without a backend field; `dictionary.py:57` similarly keys only sample and configuration. Either version these descriptors and every downstream binding consistently or introduce an explicit numerical configuration field with equivalent closure. Resource limits should remain separate from numerical compatibility where genuinely interchangeable, but current adapter resume requires exact policy and cannot silently relax that rule.

2. **An adapter owner hash does not confer ownership.** The accepted isolated adapter's `adapter.py:109–123` accepts any well-formed owner hash. Registered construction must derive that hash from a verified current `ResearchRun` claim, representation journal owner/claim, workflow, producer and pair purpose. Bind the actual experiment and execution source; never accept caller-selected owner/context hashes as proof. `lifecycle.py:75–103` exclusively publishes a run claim and rejects terminal runs, while `registered_features.py:80–118` establishes the representation owner under the lifecycle lock. Pair reservation must be subordinate to that owner, with one active handle per deterministic ordered pair and exclusive attempt directories. The lifecycle lock is not a process lease held through numerical work; the exact guard owner and cgroup must also remain authoritative.

3. **Successor source identity needs an explicit contract.** The isolated `adapter.py:78–89,138–146` compares complete context, including `source_commit`, and exact policy. Passing a new execution commit to an old pair reference therefore refuses even if numerical modules are identical. Preserve the original compatible numerical source/runtime identity only after checking its admitted byte closure, while separately binding the new execution owner to its real current claim. Alternatively refuse cross-commit reuse explicitly. Do not spoof the old commit as the new owner's source or remove source checks to make a fixture pass. Any backend, precision, typed identity, objective-domain or numerical source change requires a compatibility decision; completed scalar values do not license reinterpretation as accelerated results.

4. **Failed-parent admission and path containment must precede pair loading.** `registered_features.py:92–110` requires a failed immediate parent, no complete or active representation sibling, and a chain covering every prior representation attempt; `feature_journal.py:77–93` checks journal hashes, owner, workflow and bounded acyclic ancestry. Reuse this admitted chain. Require the referenced pair owner to correspond to that chain and its exact claim/terminal/journal, not just a directory bearing the parent ID. A run failure alone does not prove its process has died: require the retained guard/observer ownership closure before a new empirical worker resumes. Pair `safe_reference` currently requires references below its supplied root (`adapter.py:66–75`), so passing only the new journal directory would reject an ancestor checkpoint. Use a contained workflow pair root with explicit per-owner ancestry restrictions, or a new separately verified ancestor-reference API; never loosen to arbitrary filesystem or sibling references. Resolve containment and same-device constraints before creating any directories, for pair use independently of the existing sampling-only check at `registered_features.py:83–88`.

5. **A sealed journal needs an exact pair reference state.** Current `feature_journal.py:9–10,50–61,94–123` supports coarse stages and stores a component followed by an immutable event, but has no pair map. Add a versioned compact state containing pair purpose/key, owner, exact manifest path/hash, publication sequence and predecessor reference. The latest eligible reference must be determined by the verified journal event chain, not by directory glob, mtime, largest filename or a caller's old pointer. Reject rollback, conflicting publications, duplicate completed pairs and references outside admitted ancestry. Bind dictionary sample indices, hierarchy/partition identity and direction; bind MCM graph/node-order/center, dictionary representative order and motif index. Typed local graph hashes are necessary but do not establish that a pair is a member of the currently admitted dictionary or MCM workload.

6. **Publication gaps require an explicit recovery rule.** Required order is durable reservation, complete pair artifact and manifest, then durable journal event/reference. Only the published reference becomes reusable. If a crash leaves a fully saved completion without its journal event, preserve it and mark reconciliation required; do not automatically rerun the completed pair or choose the orphan as latest. A separately bounded checker may validate exact owner, reservation and artifact and append an immutable recovery certificate/reference. A partial artifact stays retained and charged; use a new publication/session identity after admitted recovery. `job.py:371–383` already leaves unsealed numerical journals for bounded reconciliation after verified worker death; extend that denominator to pair reservations, manifests and event gaps rather than making the observer load arrays. A sealed complete representation remains reusable after output-publication failure (`registered_features.py:128–144,148–171`) and must not create a new solver session.

7. **Per-session quotas are not workflow quotas.** `adapter.py:119,199–221` resets counters for each new session and reserves conservatively before publication. Registered integration needs a durable workflow-wide reservation record covering every directional pair, session, publication, partial failure, owner manifest and admitted ancestor. A successor cannot reset spent bytes or publication counts. Check the aggregate reservation before new directory or numerical allocation; count actual retained extents and filesystem allocation separately from conservative logical reservations. Reference shared ancestor files once rather than pretending they are newly copied, but include every retained physical artifact in capacity checks. Include graph/index/sample/dictionary memory plus old and new live pair states in the outer guard. A first implementation can serialize pairs and explicitly close each before opening the next; do not infer a process bound from a per-pair `32*n*m` retained-state limit.

8. **Unresolved cleanup must stop the job.** `job_payload.py:165–178` specially rethrows graph-map cleanup errors but normally converts `RuntimeError`/`OSError` into an unavailable representation and continues to the batch. Pair cleanup failure must have an equally fatal path. Preserve the primary exception and secondary cleanup evidence, close every known mapping, and prevent later numerical work or fitting when resource release is unresolved. Merely attaching a note and dropping a handle, as allowed by the isolated adapter under its caller-owned guard, is insufficient justification to continue inside that guard.

## Minimal integration sequence and acceptance tests

First promote and independently verify the six modules with ordinary imports, defaults unchanged. Then add the admitted owner/reservation/reference layer and versioned journal records before connecting numerical consumers. All representation jobs must validate the new policy, exact plan/job input name, registered hash, backend identity and reuse/arm compatibility before population production or mapping, following `job_payload.py:51–79`; direct producer calls must repeat the checks. A fake or already-terminal run, policy drift, mismatched producer, foreign lease or invalid later job must fail before pair creation.

Connect dictionary directional work first. `dictionary.py:67–74` currently computes both directions and only then writes the symmetric distance. Test interruption after A→B completion and during B→A, genuine failed-run closure, a newly admitted child, and exact resume without re-entering A→B. Compare full distance matrices, hierarchy, medoids, RNG-dependent partition order and dictionary identity with an uninterrupted scalar oracle. Keep the original capacity and sample membership; never infer symmetry of the two directional solver outputs.

Connect MCM only under the explicit backend identity. `mcm.py:27–34` and `feature_pipeline.py:135–143` currently publish complete float32 rows, with no partial-row validity mask. Add motif-level references/mask and retain the distinction between incomplete cells and valid numerical zero. Test a failure after one motif and during the next, a genuine registered child, completed-motif reuse, exact center/representative order, single final conversion to the declared output precision and complete feature/binding equality with an uninterrupted run of the same backend. This does not prove Torch parity.

The end-to-end synthetic suite should also include: changed parent/center/node order/config/source/runtime refusal before checkpoint array loading; completed pair reuse with solver entry forbidden; complete representation reuse with every pair API forbidden; duplicate live owner and omitted/foreign ancestor refusal; symlink and cross-device root rejection before writes; rollback/stale pair reference rejection; crashes at reservation, array write, manifest publication and journal-event publication; successor aggregate quota exhaustion with partial files retained; actual mapped-handle closure on success, interruption and injected cleanup failure; observer reconciliation preserving all incomplete pair entries; unchanged hashes of original failed ancestors. Use actual tiny `ResearchRun`, registered producer and job dispatch fixtures, with final model fitting stubbed only when the assertion is explicitly about feature ownership. Broader verification remains a separately named guarded run after source freeze.

## Graph10 gate impact

`job.py:27–32` discovers every Python module in the package and research directory; `_admitted` at `job.py:104–106` requires their complete source closure even when the particular graph job never calls matching. Adding six package files therefore makes the never-launched Graph10 gate-v2 insufficient. Preserve gate-v2 and its unused temp02 route. Before future dispatch, create and review an immutable gate-v3 that adds the exact six module hashes and any changed/new helper pins, while retaining all inherited experiment objects, original graph inputs, resource limits and the unadopted budget proposal. Its preflight and temporary-check routing must point to that exact gate, with new receipt identities wherever earlier helpers become stale. Do not rerun a completed temporary check or silently edit a frozen registration.

Promotion also invalidates a claim that the prior 163-file full-suite receipt covers the new maintained package. Old files can still be proven unchanged, but package promotion requires its own focused and named broad verification and corresponding new source closure. Graph10 remains the same never-claimed empirical identity only while its claim/launch paths remain absent; no amendment here spends or adopts its proposed allowance. This review changes neither the actual 32/59 accounting nor the pending financial-fit denominator.

The review does not assess implementation of the forthcoming package, prove checkpoint latency under real workloads, admit an empirical matching job, or test returns, fees, funding or exposure accounting. Those paths remain outside this source/admission requirements review.
