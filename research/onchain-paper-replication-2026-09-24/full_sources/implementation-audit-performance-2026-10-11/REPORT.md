## Findings

**P1 — current preparation can exhaust the unchanged authority deadline before numeric work. Observed availability failure, not an identified arithmetic defect.** Pilot35's original `guard/child.log:24–45` reaches `compact_mcm_batched.py:553`, `_entry_lease`, then `imported_authority_interval.py:35` initial `freshness(start)`. Thus the age was already above 60 seconds when the callback began. This is different from pilot33's rejection after completing a full callback; the 35 traceback supplies no per-phase elapsed decomposition. Source `compact_mcm_batched.py:550–553` performs `_compiled_inputs` and `_edge_inputs` between those full entry boundaries. Each genuine `run.read_input` may perform substantial authority work; byte size alone does not bound its latency. Adding an end boundary cannot repair an already stale interval. No grace, late timestamp reset or deadline widening is proposed. Measure each genuine role join and its nested validations before a further full attempt; segment only between complete legitimate validation operations, and refuse if an indivisible validation cannot fit the existing deadline.

**P2 — source authentication repeatedly compiles already authenticated source. Definite work; saving unmeasured.** `imported_authority_lease.py:51–76` freshly reads/hashes each loaded source, compiles it, recursively builds expected-code lists and compares function code. Activation calls it at :97; every scheduled `_full` at :118–124 calls it again. `_finger:110–117` separately serializes configuration, fingerprints the roster and reconstructs loaded-function identity. Ordinary callbacks remain numerous even when they do not trigger full work. A lease-owned expected-code table could remove repeated compilation while retaining every fresh body hash and live function/code check. It explicitly changes compile/audit/profiling side-effect cadence, including a possible later audit veto; it is not universally equivalent. The existing uninstalled cachecandidate02 is a prospective implementation requiring independent review, not evidence of a resolved 35 deadline. No validation-success or stat cache is justified.

**P2 — native backend checks reread five roles repeatedly, including around each advance. Definite duplication; runtime attribution unknown.** `compiled_edge_owner.py:98–112` reads/hashes source, adapter, runtime, ABI and 21,920-byte library, parses two documents and rechecks runtime properties. `current:112–121` always invokes that work before checking the actual FD/seals and native function. `acquire:123–127` calls metadata, then another current for an existing backend; borrow and `PairExecutor` add their own entry checks. `matching_immutable_session.py:185–219` invokes edge currentness before and after advancement. Thus a long pair can incur repeated filesystem reads proportional to its number of advances despite one lazy backend load per numeric owner. This preserves a stronger immediate mutable-path refusal contract than checking sealed code alone. A prospective change could retain fresh role authentication per borrow and sealed-FD/function/policy checks per advance, but must explicitly declare the changed external-file mutation detection timing and demonstrate genuine outer lease coverage. It cannot be presented as an unchanged-success cache.

**P2 — the edge extension is mostly a C-controlled Python loop, not a vectorized numeric kernel.** `edge_chunk_adapter.py:27` onward checks exact runtime/functions, readonly contiguous float64 two-column features and bounded index/count conditions. `matching-compiled-two-attribute-agreement01-2026-10-11/edge_chunk.c:16–46` uses Python scalar extraction, float conversion, subtraction, power, ordered `math.fsum`, division and `math.exp`; :47 onward performs per-element Python API operations. The GIL is held. The implementation can remove interpreter/generator overhead but retains allocation, NumPy scalar extraction and Python callbacks. Downstream `matching_annealing.py:253–254` still multiplies arrays and uses ordered `np.add.at`. Neither multicore scaling nor whole-pair speedup follows from the `.so` suffix. An entire update implemented with the same object operations may merely move the loop, while extending failure-prefix/checkpoint complexity. First compare component and whole-pair timing, then consider a truly numeric bounded kernel under the scientific tolerances below.

**P2 — three full mutable matrices are scanned at every advance. Definite linear cost; removal is not automatically safe.** `matching_annealing.py:135–156` verifies state structure and finite values in V/M/Q. Session immutable graph pins avoid repeating input-body hashing here, but `matching_immutable_session.py:209–223` still routes through this state check. For n by m matrices and A advances this adds O(A·n·m) reads and temporary finite masks, beyond actual update work. Public mutable state means checking only changed entries would weaken detection of external mutation unless a new owned-state contract is established. Measure these scans independently; investigate reducing their allocation or making ownership enforceable, preserving refusal at actual authority/checkpoint boundaries. Do not delete the scan based on an assumed private array.

**P2 — cache construction and validation repeat across occurrences. Correctness guards are substantive.** `batched_numeric_reuse.py:259–286` validates a pair, checks policy, computes both graph identities, constructs a full framed key from config and six arrays, hashes/looks it up, and reconstructs the key after execution. Computed misses then repeat validation at executor/create/session layers (`batched_pair_executor.py:85–91`, session :76 onward). The key includes actual numerical bytes; hash buckets also compare exact key bytes (:204 onward), and LRU storage is capped. Parent/node labels are not numerical keys; this does not grant independent scientific occurrence credit. A row-local immutable numerical-key component or once-per-row local identity could avoid repeated byte copies, but only with explicit immutable backing identity and unchanged fresh authority/purpose joins. Public mutation semantics and callback order must be tested, rather than treating validations as redundant by appearance.

**P2 — current reuse and native eligibility partition the workload.** `matching_annealing.py:176–184` caches edge weights only within one advance when E≤4096 and the advance budget exceeds E; the selected adaptive policy extends this to E≤16384 with fixed 256-entry chunks/262,144-byte scratch. Cache arrays are recreated each advance. Native edge fill at :227 is selected only when `not reuse`; its maximum chunk is 1024 and several shape/runtime checks can fall back. The tiny compiled logsumexp helper (`compiled_small_lse.py:125–138`) requires both block dimensions 1..4, finite float64 magnitude≤256 and exact runtime conditions. Its C reduction uses libm exp/log/log1p; old finite results cannot prove universal SciPy equality. Large matrices often retain SciPy reduction and Python edge work. Count actual accepted/refused chunks and refusal reasons by safe scalar geometry before choosing the next accelerator.

**P2 — checkpoint costs can grow with retained history.** `compact_mcm_batched.py:165–190,388–404` inventories and hashes the complete checkpoint tree before/after each save and again after the authority boundary. `matching_checkpoint.py:80–88` switches from annealing into dense M hashing and hardening creation; these atomic tasks are not simply edge-operation units. Checkpoint saves write the dense matrices and durable metadata (`matching_annealing.py:314` onward). Repeated full inventories of cumulative retained bytes can make total checkpoint I/O superlinear in checkpoint count. This is a source complexity finding, not evidence that checkpoints caused the observed first-batch delay. Preserve durability/currentness; measure actual inventory bytes/time separately before considering an authenticated incremental inventory design.

## Work and callback model

With n,m node counts, E the product of edge counts, d node/edge attribute dimension and T annealing iterations (original configuration unchanged), basic work is O(n·m·d + T·(E·d+n·m)), excluding validation, hardening and callback work. Retained V/M/Q alone require 24·n·m bytes; this is not a complete peak-memory bound. No RNG occurs in this annealing body; sampling randomness elsewhere remains part of the protocol.

Reuse of the earlier driver source analysis is valid for its unchanged successful streaming structure: journal forces two producer boundaries per completed batch, not one per cell. Direct ordinary polls through the first summary are `3+2R+2N+3C+A`, with N occurrences, R rows entered, C computed pairs and A total advances. Each ordinary poll can trigger scheduled full validation. This is not a full-hash count or observed runtime count. Driver reuses a local neighborhood across 32 motifs but the memo still creates each numerical key. These facts argue for phase-specific accounting rather than inferring a stall from a durable pending marker.

No new definite mathematical defect, cache collision bug or cleanup defect was established in this bounded inspection. In particular, memo poison retains primary errors and attempts captured executor cleanup (`batched_numeric_reuse.py:242–258`). That statement is limited source inspection, not general correctness certification.

## Evidence limits and scientific acceptance

Pilot34 terminal review records 9 partial batches: 36,864 cells, 35,744 computed, 1,120 reused (about 3%), and 5,215.995 seconds summed numeric elapsed versus 10,775.518 guard elapsed. The difference cannot all be attributed to authority overhead; initialization, other phases and interruption are included. These partial batches are not completed MCM/training or whole-run throughput. Root's earlier first-batch observation of 2,192.79 seconds internal authority polling out of 3,915.77 numeric seconds is a specific batch observation, not an all-run fraction.

The retained native03 review reports 147 native chunks, 130 bitwise-equal state advances, equal assignment/score and late overflow prefix. Tiny fixture kernel timings were 0.027782 seconds baseline versus 0.023880 candidate, with 0.015693 seconds for only one of two currentness checks per advance. This proves finite exercised compatibility, not a real-data saving or useful full-run speedup.

Frozen `REPLICATION_SPEC.md:194–195` requires C05 float64 matching feasibility and scalar agreement at atol1e-8/rtol1e-6; C06 accelerated float32 forward/similarity uses atol1e-5/rtol1e-4, with tie feasibility/score criteria. Lines209–214 explicitly reject universal bitwise identity as a general GPU/tie requirement and prohibit casually widening failed tolerances. Exact bitwise state/error-prefix checks are valuable engineering regression criteria for the presently selected narrow seam; they are not the universal scientific requirement. A separately specified accelerated implementation may target the frozen applicable tolerance, preserving method, iteration, sampling, budget, checkpoint and failure contracts. It must not silently relabel an exact seam as tolerant or use C06 to waive C05 obligations.
