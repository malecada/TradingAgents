# Registered failed-chain precheck

The new isolated `ancestry.py` connects an actual active `ResearchRun` to the
accepted failed-owner death checker. It reads only compact metadata, performs no
process action or numerical allocation, and is not yet imported by a maintained
producer. Source and numerical package files remain unchanged. This is one
prerequisite for production checkpoint continuation, not admission to continue.

The active run must admit the exact executing ancestry/death sources, fit
representation route, version2 producer plan, pair policy, immediate failed
journal and ordered death-evidence input. The registered descriptor determines
the workflow directory. Every existing representation attempt must be accounted
for by the exact failed-parent chain; the successor directory must not yet exist.
The current child claim cannot be fake or terminal. Each compact file is bounded
to2MiB, regular, single-link, nonsymlink and on the root filesystem. No-follow
reads verify type/inode/extent/change signatures and any supplied hash.

For each of at most8 ancestors, owner/start/claim/failed-journal identities must
join the original lifecycle claim and immutable historical registration. Its
historical admitted execution job and producer plan must declare the same
representation, descriptor, producer, policy and output route. A declared
continuation must point to exactly the next failed sibling and the registered
hash before that parent file is opened. A first representation can have no
representation parent even if its lifecycle parent concerns an earlier stage;
it must explicitly have no representation continuation or death input. A
complete representation or representation-complete event requires the separate
reuse route rather than continuation.

Every ancestor then passes the existing full compact death-observation check.
The entire chain is observed again before return, followed by an inventory
check covering all siblings, lifecycle/representation completions and optional
final guards. Every retained file signature is checked again after these joins.
This is a checked snapshot under the future outer owner's exclusive execution
contract; it is not a lock or a guarantee that mutable OS state cannot change.
Cross-boot and supervisor PID reuse retain the earlier conservative refusal.

The return value explicitly records `continuation_admitted=false`,
`numerical_compatibility_verified=false`, `outputs_verified=false` and
`arrays_read=false`. Full fit-job/resource policy admission, the active child's
guard lease, numerical source/runtime compatibility, graph/pair workload
membership, feature event payload integrity, checkpoint/orphan reconciliation,
whole-workflow quota and numerical consumer routing remain mandatory. No claim
is made that an admitted metadata route alone is executable or scientifically
valid. No empirical claim, resource allowance or financial fit is consumed here.

## Verification and corrections

All fixtures use temporary real Git repositories, actual `ResearchRun.start`
and failed terminals, actual `FeatureJournal` owners and a newly admitted child.
Only OS boot/PID/cgroup predicates are mocked. No empirical source, saved array,
historical run or closed engineering profile is replayed.

`red01.log` retains17 missing-component failures. `green01.log` retains17 passes
in6.745s. Additional registered malformed-contract tests and adversarial mutation
tests were added before correcting independent findings A1–A3:

- A1: the parent path was read before its exact workflow location was checked.
  `red02.log` retains25 tests with the foreign-read counterexample failing;
 24 passed, including a lifecycle-completion race already refused by admission.
- A2: a previously absent final guard for an earlier ancestor could appear while
  a later ancestor was checked. `red03.log` retains that failing counterexample.
  Whole-chain death and final-inventory checks now follow the initial traversal.
- A3: journal metadata could erase a historical registered continuation.
  `red04.log` retains a genuinely admitted child with that malformed historical
  chain being accepted. Historical job/plan/path/hash joins now refuse it.

Original source and the expanded pre-fix tests are retained. `REVIEW.md` is the
initial withheld-acceptance review and remains immutable. `green02.log` records
28 passing tests in10.966s, covering the corrections, exact read-only two-parent
joins, first/current owner exclusion, foreign/missing/duplicate/reversed/too-deep
ancestry, policy/schema changes, live ancestor/whole-chain rechecks, source and
input drift, symlinks, completed owners and mutations during observation.
Later review evidence, if present, supersedes the initial acceptance decision
only for the exact corrected source identified there.

The previously completed maintained-package offline verification is not rerun:
this addition is isolated outside that package, whose source bindings remain
unchanged. The targeted new synthetic suite verifies this component; the earlier
suite does not establish integrated successor or dictionary/MCM correctness.
That integrated work still requires its own appropriate verification.
