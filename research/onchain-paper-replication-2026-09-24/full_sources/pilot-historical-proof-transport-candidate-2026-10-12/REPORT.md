# Historical proof transport candidate — WITHHELD

The persistent-reader candidate fails a required fresh-currentness control and must not be integrated. No live source, Gate, actual claim/history or numerical job was changed or executed. All Git activity used tiny temporary synthetic repositories, except a read-only Git version query. Test runtime was the pinned .venv Python. Temporary repositories were removed by fixture cleanup.

The final candidate copies change only admission.claims ownership and verify's source-proof transport. One lazy, sweep-owned Git2.34.1 `cat-file --batch` process handles the existing128-request/64KiB request batches and8MiB body ceiling. Every original commit:path request and body is retransmitted, and original `_verify_batch` SHA256/semantic ordering is retained. Default verify_claim/_verify_sources behavior outside the explicit reader remains unchanged. There is no application OID-body, path, stat or validation-success cache. Registration, extension, binding, family, input, output and spent-record checks are not skipped. Reader retirement kills/reaps/closes on consumer abort and errors; normal retirement closes input, drains to EOF and rejects trailing output.

Nine focused controls pass in GREEN05: exact six-claim old/new result equality, unique/mismatched/missing bodies and original hash-before-missing priority, fresh claim mutation, wrong scope/closed-reader refusal, consumer abort retirement, framing/request limits, actual child timeout/truncation cleanup, oversized-body semantic ordering and fatal cleanup priority. The bounded six-claim actual-Git fixture records12→7 child starts, with2,444,544 returned bytes in both paths. This is a42% child-count reduction on the synthetic fixture, no byte reduction and no measured actual-pilot speedup.

The decisive additional control is REPLACE_CURRENTNESS01.json, produced by probe_git_replace01.py in a temporary repository. After warming the candidate reader with the original commit, a different synthetic source commit was created and installed through `git replace(original,new)`. A fresh legacy child then rejected the expected hash with `registered source/charter/selection hash mismatch`; the already running candidate child accepted the old proof. Git's retained internal object/replacement state makes repeated commit:path requests insufficient to reproduce the fresh-child behavior. No claim or application-level success cache is needed for this regression. The current source authenticity contract does not authorize ignoring replacement changes.

Preserved iteration01 implements fresh header resolution plus OID-body reuse under8MiB/128 entries. Its six-claim fixture reduced returned body bytes but increased total child starts; it was superseded, not installed. Preserved iteration02 tried a single mixed info/contents child, but installed Git2.34.1 does not support `--batch-command`; its failed test and retired-child evidence remain. The final supported persistent reader fixes that capability issue but encounters the independent currentness regression above.

Literal and AST forward/inverse patches and original/candidate source hashes are retained. Existing successful controls do not override the failed mutation control. A safe next decision is required from Root: retain fresh children, or explicitly review a separate mechanism proving all Git resolution state current at each semantic boundary. Setting GIT_NO_REPLACE_OBJECTS, trusting a repository fingerprint, skipping replacements, or treating warmed Git as immutable would change the current contract and is not supplied as a silent workaround. Fresh-header/OID-body iteration01 also remains unqualified and is not recommended for integration without its own mutation/failure review.

Original38 remains closed/spent. No full39 builder, binder, claim or history verification was run. Actual38's179 admissions/1417.960485s justify examining this seam, but do not establish that process startup rather than Git object decoding dominates. The candidate's failed freshness control is an exact blocker, not evidence to relax provenance.

## Narrow next-design assessment

No safe transport-cache successor is presently established. Fresh header resolution alone does not detect changed object content under an existing OID: omitting a fresh body read can miss corruption/replacement-related changes, while the persistent reader demonstrably misses fresh replacement resolution. Retaining fresh child and body reads preserves that behavior but removes the claimed startup/byte saving. Do not disable replacement refs or substitute stat/path fingerprints. A separate fixed metadata transaction using the already admitted read_inputs entry/exit protocol might remove redundant complete admission calls, but only if a concrete remaining caller bundle has more than two admissions and independently reviewed dependency/callback order. No such additional bundle is proven here; it is a design avenue, not an implementation recommendation. Accepted verification can serve full39 without this acceleration.
