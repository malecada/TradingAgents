# Verification sharing boundary challenge

Decision: no useful semantics-equivalent historical-success sharing boundary was found inside one current imported full callback. An ordinary ImportedExecution.check performs two PreparedImport._check calls; each reaches Binding.check and a full ResearchRun._check_source admission. Keeping fresh historical proofs at entry and exit therefore preserves two sweeps, not one. A success cache is not justified by the lifecycle lock or source fingerprints.

The larger composite batched boundary (Target.check, Owner.boundary, Target.final) contains three forced full leases plus one direct Binding.check: seven historical sweeps. The parallel hotpath investigator reports an earlier measured batch delta of nineteen full leases plus four direct owner checks, giving42 admissions. These are different units:42 is not one full callback. Seven-to-two is a concrete possible reduction of five sweeps per composite boundary, but only under an explicitly changed historical-proof sampling contract. No elapsed speedup follows from this static arithmetic or earlier claims-component measurements.

## Current checks that sharing must preserve

ImportedExecution.check enters through stage.lease, which calls PreparedImport._check. Prepared checks its exact Binding/Run/capability configuration, calls Binding.check, verifies original evidence, reselects the job/plan and rejoins source/configuration. Binding.check separately performs active claim checks, full admission, all registered input hashes, fresh committed numerical-source bytes, runtime inventory and live owner/journal/guard checks. ImportedOriginal rereads original bodies across its authority callback. Execution builds metadata, repeats Prepared checking, then rejoins matching bytes, current owner, stage contents and materialized integrity before returning. Lease._full additionally authenticates loaded code and verifies Target metadata. Scheduler clock/live/fingerprint callbacks can follow the full callback; the existing checked-value path performs another final rejoin after those callbacks.

The expensive claims result is only one input to admission. Every admission must still observe current registration/design/charter/source bytes, runtime hashes, source closure, input declarations and bindings; rescan current claim roster; detect partial claims, contradictory terminal markers and active-run changes; recalculate current family budget, cumulative extension adoption/snapshot/terminal checks, parent status and sample exposure. Historical claims being unchanged does not authorize returning a previous Admission or budget decision. A newly present claim consumes an attempt even if failed. There must be no fallback to an earlier successful result after a new refusal.

verify_claim depends on the actual claim bytes and fresh historical Git registration/design, source/charter/selection, extension/review, binding and capture bodies. It does not prove an entire terminal/output tree. Existing claims checks add terminal contradiction detection; effective_budget independently reads required claim and terminal bodies and extension metadata. These separate dependencies cannot be silently dropped or broadened into a claim of full historical output verification.

## Why file snapshots cannot authorize historical-proof reuse

The live Git semantics include replacement refs and object availability/content. A claim path/hash/mtime or unchanged research_runs roster does not prove current historical Git bodies. The lifecycle flock coordinates participating claim writers only; Git commands and external filesystem writers do not honor it. Full source/input fingerprints similarly do not cover every Git dependency. The earlier persistent-Git candidate was withheld for an actual replacement-currentness counterexample; merely shortening a cache to one callback does not remove that counterexample.

Fresh full proofs at both ends detect a persistent change at those ends. They do not detect a change then restoration at an omitted former checkpoint. The old implementation could reject there. Such an omission changes observation points, refusal order and latency even if both versions are sampled and neither supplies atomic writer exclusion. It must not be described as temporal equivalence or unchanged fresh proof.

## Concrete boundaries

1. **Recommended first candidate if unchanged freshness is required:** retain every current historical Git-body rejoin and claim/roster read. Share only deterministic decoded/validated values whose entire actual input-byte transcript is freshly reproduced at that very checkpoint. Scope is one exact Run/root/source/design/registration/claim invocation; discard on exit or any failure. This can remove repeated JSON/schema work, not the expensive fresh byte proofs. No material performance gain is established. Avoid replacing fresh Git processes with a persistent transport whose ref/object view can become stale.

2. **Potential high-impact candidate requiring an explicit changed contract:** the single synchronous metadata-only composite boundary in compact_mcm_batched.produce, rather than a whole batch, solver, publication, transport or interval lifetime. It may use one fresh full historical proof at entry and one at exit, with the original nonhistorical admission, live claim/roster/terminal/budget/input/source/runtime checks retained at each internal checkpoint. Seven-to-two is a static upper opportunity, conditional on exact trace and no nested extra boundaries. No result, numeric advancement, file publication, archive operation, claim creation or success grant may escape before final proof and post-callback metadata/input/code rejoin. This is a new bounded historical-proof sampling policy; acceptance requires explicit source/schema review and adversarial mutations, not an assertion that a cache is safe. Current instructions do not release this policy.

3. **One ImportedExecution.check alone:** keep its current two fresh endpoint sweeps. Wrapping it in another two-proof transaction adds complexity without removing historical sweeps. PreparedImport._check alone has one direct historical sweep. The prior same-boundary metadata-result seam has already removed the redundant extra execution check; it is not a fresh remaining optimization.

## Required transaction properties for any selected candidate

The participant must be an exact genuine same-Run/Binding/Owner/Prepared/execution chain with fixed source and registered selector. It must not accept a caller-supplied list, arbitrary callback token or mutable global success marker as authority. Store immutable byte results and identity pins, not mutable Admission/claim dictionaries reusable by other callers. Loaded module/function/code/closure roster checks and full source proofs remain outside any reused predicate result. Final failure poisons/refuses the transaction; it never publishes the cached value.

Do not hold the existing non-reentrant lifecycle flock over callbacks which invoke read_input/read_inputs or a nested _check_source path. The prior continuation fix places polls outside those locked transactions for exactly this reason. Either retain existing individual lock scopes or design a separately reviewed explicit unlocked inner operation under a single known lock owner; switching to an RLock or skipping an unknown nested lock is not equivalent. A cooperative root lock cannot be sold as Git writer exclusion.

ContextVar isolation alone is insufficient: asynchronous task context copying can inherit its value. Any scoped proof needs exact thread identity, task/owner scope when applicable, single active non-reentrant use, a finite lifetime, and rejection on foreign Run/root or inherited concurrent context. Parallel claims workers must receive only finite immutable proof inputs, never a transferable authority grant. Already launched work must be drained on failure; no completed success may escape uncertain cleanup.

Preserve original ordinary error ordering where retained. A later exit proof or cleanup failure must not replace the original fatal BaseException; secondary failures must be recorded defensively, including hostile add_note/string formatting. No new failure may trigger retry, silent sequential/cached fallback, extra grant or unknown worker survival. Exact detection timing changes must be documented. Final source/input/metadata checks must occur after the last potentially mutating callback, with no later callback capable of invalidating the returned result.

No live source edit, implementation framework, authority construction, admission, claim, numerical/data-array import, historical-proof execution, benchmark, network action or unchanged test matrix was performed. This report is a source/design challenge, not source release or empirical admission.
