# Terminal event accounting: engineering design and verification plan

Scope authorized by the September 10 instruction to implement settlement and funding accounting. This extends the admission design in `docs/settlement-evidence/accounting-admission.md`. Baseline: `d9d6a3ede6d80f4c46024ea27b296860e51cd7db`. Only synthetic engineering checks are authorized here; no market-data fetch, financial trial, gate amendment or historical replay is performed by this implementation.

## Interface and ordering

Add `tradingagents/event_accounting.py`, keeping the frozen bar engine and historical callers unchanged. `run_event_book` accepts absolute boundary prices, target weights, stable original-contract specifications, settlement records, and either an explicit funding exclusion (`None`) or funding inputs with an independently declared complete calendar. It returns period returns, boundary quantities and an event ledger. This is a separate API because bar returns and daily summed funding cannot reconstruct event prices or terminal cashflows.

The price panel must contain every boundary from the inclusive start through the inclusive end at the declared fixed frequency. Targets may occur only at boundary starts, never the final end. Missing/all-NaN target rows retain units; explicit target rows use zero for omitted symbols. Held prices must be available before a requested flat exit. Event times must be timezone-aware and are normalized to UTC.

The caller must explicitly select the supported `events_before_targets` policy: timestamped funding and settlement occur before boundary valuation and trading. Simultaneous external events require unique explicit sequence numbers; list order is immaterial. Other boundary orderings are unsupported and fail. Forced settlement always values incoming quantity, including when the boundary target is flat. Funding at termination may precede or follow settlement according to its declared sequence. Events at the final boundary belong to the final reporting period. Initial-boundary events see an initially flat book.

The linear book stores signed contract quantity and the preceding valuation price. A multiplier converts contracts into base units. Mark PnL is `q * multiplier * (new_price - previous_price)`. Funding uses its own event mark as a cash basis, without changing the preceding book valuation. Terminal MTM is booked once, the admitted settlement commission is charged once, quantity becomes zero, and the original identity cannot reopen. Successors require distinct identities and never inherit quantities.

## Admission and unsupported behavior

Contract specifications declare venue, original identity, collateral, linear type, listing, optional termination/reduce-only timestamps, multiplier, quantity step (or explicit continuous sizing) and evidence reference. Evidence references retain source identifier, SHA-256 and whether inputs are synthetic, observed or a registered model; this is traceability, not automatic source authentication. Supplied prices are already admitted/rounded marks. Fees use an explicitly supported absolute-notional basis and an explicit cash-rounding rule. Funding cashflows have their own rounding rule. Unsupported product/basis/order rules fail.

A funding calendar must span the whole requested window and name every contract, including explicit empty schedules. Expected funding records may be absent/unknown: an exposed book then fails; an unheld/terminated contract incurs no phantom cashflow. Calendar completeness is an external evidence assertion, not something inferred from the records. Scheduled settlements likewise fail if required fields are missing while held. Missing funding, fee, terminal price, multiplier or event ordering must never become zero by inference. Daily-summed funding inputs are unsupported.

Reduce-only checks compare actual contract quantities after NAV and price drift. Reductions to zero are allowed; increased absolute quantity or a sign flip is rejected. Zero price may value held contracts but cannot size a nonzero target. NAV must remain finite and positive. No leverage-margin/liquidation, inverse payoff, execution slippage, partial fills, live deployment or historical data-admission claim is added.

## Implementation and acceptance sequence

1. Add hand-derived synthetic cases in `tests/test_event_accounting.py`, run them against the missing API, and retain the expected failing result. Cases cover long/short settlement, multiplier and quantity drift, fee/closure exactly once, funding marks before/at/after closure, complete reporting clock, unknown required inputs, same-time ordering, restrictions and separate successors.
2. Implement the standalone event path. Return dollar components alongside normalized period returns so NAV reconciliation is independently inspectable. Do not attach legacy `BookInputs` or expose this result to the legacy approximate overlay path.
3. Add adversarial cases identified in independent review, observe failure before fixes, and run the synthetic suite plus existing accounting/lifecycle regressions. Verify that historical code, gates, results, ledger and archived input snapshots remain unchanged.
4. Record validation, limitations and the support-contact outcome; commit and push the reviewed engineering branch. A future carry/momentum/liquidation-fade adapter and empirical replay require a fresh committed research registration and admitted inputs. Existing 2 conditional failures / 22 unavailable accounting cases remain unchanged.

The supported formula paths are deliberately explicit models. Passing these tests establishes bookkeeping behavior, not Binance historical rule applicability or a validated strategy.
